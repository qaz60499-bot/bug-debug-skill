# 07 — Firmware / IoT

> 用于自有设备、实验设备或明确授权固件的分析。

## 分层

```text
container
→ partitions/filesystems
→ configs/certs/scripts
→ services/binaries
→ protocol/update/boot chain
→ emulation or hardware observation only when needed
```

## 第一遍地图

记录设备型号、版本、升级包格式、签名/完整性元数据、分区/文件系统、init 脚本、服务配置、证书、Web 资源、服务二进制和监听配置。

提取出的 ELF/共享库直接进入 native reference，不在固件层重复一套方法。

## 可验证解包与启动链

先核验下载文件长度、SHA256、镜像头与分区边界；缺失字节的 `.part` 和 Git LFS pointer 必须拒绝。只有目标完整且 `unblob`/专用解包器通过当前主机的工具验证，才在隔离输出目录限制深度和资源地提取；每层记录输入哈希、偏移、输出文件哈希和失败区间。后续逐项证实 init/rcS 配置→实际调用脚本→可执行服务文件→ELF/库依赖，而不是仅凭源码目录存在就声称设备服务实际启动。动态行为须另作隔离验证。

## Daemon / 用户态仿真的动态验收门槛

`qemu-user -L <rootfs>` 只可验证受限目标的用户态指令和共享库装载；它不会自动复现目标的 `/etc`、Flash 伪设备、内核模块、网络接口与真正设备启动。分别记录客体 ELF 运行、进程创建、服务就绪、协议响应，不得互相替代。

对于 `fork`/daemon 化服务，**父进程 exit(0) 不是服务成功证据**：必须继续观测子进程的系统调用、关键返回值、退出/存活状态，并在必要时用隔离的真实请求验证服务端点；错误参数触发诊断但父进程仍 exit(0) 的情形作为负例。若出现 `EPERM` 原始套接字、缺失 Flash 伪设备、目标 RootFS 未完整映射等，标记 `PARTIAL` / `BLOCKED` 并记录原因，不升级为运行时 `PASS`。不得为了强行通过而开放宿主网络或不受控权限。

## 仿真

只有静态证据不足以回答具体运行时问题时才考虑用户态或系统仿真。先写明要验证的问题、输入、预期观察和停止条件。

## 工具安全

未知固件与第三方解析脚本均视为不可信输入；分析工作区与日常敏感目录隔离。
